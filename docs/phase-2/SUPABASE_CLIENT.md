# Supabase Client — Phase 2

> **GATE AIR-1 Command Center** · Phase 2  
> How `src/lib/supabase/server.ts` works, when to use `supabaseAdmin`, and the rule against browser exposure.

---

## Overview

Phase 2 uses **two distinct Supabase client patterns**:

| Client | Location | Key Type | RLS | Use Case |
|--------|----------|----------|-----|---------|
| `supabaseAdmin` | `src/lib/supabase/server.ts` | Service Role Key | Bypassed | Server-only mutations, import pipeline |
| `supabaseBrowser` | `src/lib/supabase/client.ts` | Anon Key | Enforced | Client component reads (Phase 3+) |

## `src/lib/supabase/server.ts`

### Full Module

```typescript
// src/lib/supabase/server.ts
import 'server-only';
import { createClient, SupabaseClient } from '@supabase/supabase-js';
import type { Database } from '@/types/supabase.generated';

// Fail fast at module load time if env vars are missing
const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL;
const serviceRoleKey = process.env.SUPABASE_SERVICE_ROLE_KEY;

if (!supabaseUrl) {
  throw new Error('NEXT_PUBLIC_SUPABASE_URL is not set');
}
if (!serviceRoleKey) {
  throw new Error('SUPABASE_SERVICE_ROLE_KEY is not set');
}

// Singleton — created once per server process
let _adminClient: SupabaseClient<Database> | null = null;

export function getSupabaseAdmin(): SupabaseClient<Database> {
  if (!_adminClient) {
    _adminClient = createClient<Database>(supabaseUrl!, serviceRoleKey!, {
      auth: {
        autoRefreshToken: false,
        persistSession: false,
      },
    });
  }
  return _adminClient;
}

// Convenience export — prefer this in services
export const supabaseAdmin = getSupabaseAdmin();
```

### Key Design Decisions

#### `import 'server-only'`

This zero-byte import from the `server-only` npm package causes a **build-time error** if this module is ever imported from a client component or a file without `'use server'`. It acts as an enforced boundary.

```
Error: This module cannot be imported from a Client Component module.
It should only be used from a Server Component.
```

#### Singleton Pattern

The admin client is created **once per Node.js process** (or per Edge Worker instance in serverless environments). Creating a new client per request is wasteful because the underlying HTTP client and connection pool are reinitalized unnecessarily.

#### `autoRefreshToken: false`

The admin client uses the service role JWT, which does not expire (it is a permanent service key). Auto-refresh would make unnecessary calls to the Supabase Auth server.

#### `persistSession: false`

The admin client has no user session to persist. Disabling session persistence avoids unnecessary reads/writes to cookies or localStorage (which would throw in a server context anyway).

## `supabaseAdmin` vs `supabaseBrowser`

### When to Use `supabaseAdmin`

Use `supabaseAdmin` when:

- ✅ Writing data to any Phase 2 table (all writes require service role)
- ✅ Reading from `import_batches` or `import_row_results` (no public read policy)
- ✅ Performing upserts that bypass RLS by design (subjects seed, lecture upsert)
- ✅ Any operation inside a service file (`src/server/services/`)
- ✅ Any operation inside an API Route Handler that mutates data

### When NOT to Use `supabaseAdmin`

Do NOT use `supabaseAdmin` when:

- ❌ In any file that might be imported by a client component
- ❌ In any `'use client'` file
- ❌ In any React Server Component that renders user-facing content (prefer the browser client with user session for user-scoped reads)
- ❌ For reads that should be subject to RLS (e.g., reading a specific user's data)

## Import Rules

### In Services (Correct)

```typescript
// src/server/services/curriculum.service.ts
'use server';
import { supabaseAdmin } from '@/lib/supabase/server'; // ✅

export async function getCurriculum() {
  const { data, error } = await supabaseAdmin
    .from('subjects')
    .select('*, topics(*, subtopics(*, lectures(*)))')
    .order('display_order');

  if (error) throw error;
  return data;
}
```

### In Route Handlers (Correct)

```typescript
// src/app/api/v1/curriculum/route.ts
import { getCurriculum } from '@/server/services/curriculum.service'; // ✅

export async function GET() {
  const data = await getCurriculum();
  return Response.json(data);
}
```

### In Client Components (NEVER DO THIS)

```typescript
// src/components/SomePage.tsx — CLIENT COMPONENT
'use client';
import { supabaseAdmin } from '@/lib/supabase/server'; // ❌ Build error!
// The `import 'server-only'` in server.ts will cause this to fail at build time.
```

## Generated TypeScript Types

The Supabase client is typed with `Database` from `@/types/supabase.generated`, which is generated by:

```bash
npx supabase gen types typescript --project-id lcotzvvckbxhmsasicwr > src/types/supabase.generated.ts
```

This must be re-run whenever the database schema changes (after applying migrations).

### Usage

```typescript
import type { Database } from '@/types/supabase.generated';

type Subject = Database['public']['Tables']['subjects']['Row'];
type InsertLecture = Database['public']['Tables']['lectures']['Insert'];
```

## Connection Pooling in Serverless

In serverless environments (Vercel Edge Functions, Vercel Serverless Functions), each function invocation may run in a fresh process. The singleton pattern in `server.ts` creates a new client **per cold start** — this is acceptable because the client is lightweight (it's just an HTTP client wrapper, not a persistent TCP connection).

For Phase 4+, if query volumes increase significantly, consider connecting via **Supabase's pgBouncer** connection pooler (port 6543) for direct SQL connections using `postgres.js` or `pg`.

## Logging and Error Handling

The `supabaseAdmin` client does not throw on query errors by default — it returns `{ data, error }`. All service functions check for errors:

```typescript
const { data, error } = await supabaseAdmin
  .from('subjects')
  .select('*');

if (error) {
  console.error('[curriculum.service] Failed to fetch subjects:', error);
  throw new Error(`Database error: ${error.message}`);
}
```

Errors are logged to the server console (captured by Vercel's log drain or local terminal) and re-thrown as standard `Error` objects that Route Handlers can catch and return as `500` responses.
